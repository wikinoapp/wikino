## 概要

<!--
ガイドライン:
- この機能が「何であるか」「なぜ必要か」を簡潔に説明
- 2-3段落程度で簡潔に

ページの同時編集機能を実装する。複数のユーザーが同じページを同時に編集できるようにすることで、リアルタイムなコラボレーションを実現する。

基本的なフローは VS Code の Live Share に倣う。ページ編集画面で共同編集セッションを開始し、生成された URL を他のユーザーに共有することで、同じ下書きに対して複数人が編集を行える。

共同編集用の URL を生成する方式を採用する理由は以下の通り：

- **下書きの基準が明確**: セッションを開始したユーザーの下書きを元に編集するため、「誰の下書きを使うか」の問題が発生しない
- **意図的な開始**: ユーザーが明示的に共同編集を開始するため、意図しない同時編集が始まることがない

### ユーザーフロー

1. User A: ページ編集画面を開く
2. User A: 共同編集ボタンを押す
3. システム: 共同編集セッションを作成し、共同編集用の URL を生成する
4. User A: URL を User B に共有する
5. User B: URL にアクセスする
6. システム: User B を User A の共同編集セッションに参加させる
7. User A と User B が同じ下書きをリアルタイムに編集できる

### 検討が必要な設計課題

以下の設計課題は、実装フェーズに入る前に方針を決定する必要がある。

#### リアルタイム同期の方式

同時編集の核心は競合解決である。主な選択肢：

- **OT（Operational Transformation）**: CodeMirror 6 の `@codemirror/collab` パッケージが OT ベースの協調編集をサポートしている。サーバー側で操作の変換処理を実装する必要がある
- **CRDT（Conflict-free Replicated Data Type）**: Yjs などのライブラリを使用する方式。サーバーの実装がシンプルになる傾向がある

#### 通信方式

- 現在 Datastar（SSE）を使用しているが、SSE はサーバー→クライアントの一方向通信
- 同時編集では双方向の低レイテンシ通信が求められるため、**WebSocket** の導入が必要になる可能性がある
- SSE + POST リクエストの組み合わせで実現可能かどうかも検討する

#### セッションのライフサイクル

- セッション開始者（User A）が離脱した場合のセッションの扱い
- 接続が一時的に切断された場合の復帰方法
- 共同編集 URL の有効期限
- 同時接続数の上限（2 人限定 vs 複数人）

#### 下書きの保存と公開権限

- 共同編集中の下書き保存は誰が行えるか（セッション開始者のみ or 全参加者）
- ページの公開（保存確定）は誰が行えるか
- 共同編集中のオートセーブの挙動

#### 参加者の既存下書きの扱い

- User B が同じページに対して既に下書きを持っている場合、共同編集セッションに参加するとどうなるか
- User B の既存の下書きは保持するか、破棄するか

#### アクセス制御

- 共同編集 URL を知っていれば誰でも参加できるのか、スペースメンバーに限定するのか
- 参加者に対する権限レベル（編集のみ、閲覧のみなど）の区別は必要か

### ページ編集画面へのアクセスで自動的に同時編集を開始する方式

共同編集用の URL を生成せず、ページ編集画面にアクセスしたらすぐに同時編集ができるようにする方式を検討した。

**不採用の理由**:

- 複数ユーザーがそれぞれ下書きを持っている場合、どの下書きを元に同時編集すればよいか判断できない
- ページ編集中に意図せず他のユーザーが参加して同時編集が始まると、ユーザー体験として不自然になる
  - 「誰か入ってきた…」と一瞬の緊張が走る (個人の感想です)
